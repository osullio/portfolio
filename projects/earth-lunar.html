Overview

A client/server system that simulates a ground station on Earth talking to a lunar rover. The client sends commands. The rover replies with messages, temperature logs, movement confirmations and status reports. The link is deliberately unreliable: packets are delayed by the Earth–Moon light-travel time (up to about 1.36 s) and can have bits flipped in transit, so the protocol has to detect errors and recover from them.

Protocol design

Each message is a 24-byte header, packed by hand with bit shifts and modelled on TCP, followed by a UTF-8 payload.

Reliability

  • Error injection: each send has a 10% chance of having bits flipped (1% per bit).
  • Detection: the receiver re-runs the checksum, and a result of 0 means the packet is intact.
  • Recovery: stop-and-wait with ACK/NAK. Corrupted packets trigger a resend, timeouts trigger a resend, and the server drops a client after more than 10 bad packets in a row.
  • Concurrency: the server runs each ground-station client on its own thread.

What I learned

  • Length-prefixed framing is how you handle TCP's byte stream reliably, rather than hoping each recv() returns a whole message.
  • Building the reliability layer on top of TCP hides what it's really doing. Real transport-level recovery needs UDP.
  • Stop-and-wait has very low throughput on a high-latency link, which is why sliding-window protocols exist.

What I'd do next

  • Move to UDP and use sequence and ACK numbers properly (Go-Back-N).
  • Checksum the header separately so a corrupted length field can't desynchronise the stream.
  • Add unit tests for the header, checksum and bit-flip functions.
